## Summary

> **Since 2026-09-14** the agent also fronts tmux on a Linux host and the app pairs with several hosts; where this write-up says "the Mac" or "the Mac agent", read "the host" -- see [overview](../overview.md) for the current shape.

This feature area is the network and process architecture that lets an Android phone remotely drive `cmux` (a native macOS AI-coding-agent orchestrator) from anywhere on the internet. It consists of three architectural layers built in sequence: (1) a Mac-resident `term-bridge` daemon that wraps cmux's CLI/socket in a small authenticated HTTP/WebSocket API, (2) a `term-bridge-relay` rendezvous service on a home server that lets the Mac "dial out" through NAT so the phone can reach it through one public mTLS endpoint, and (3) a multi-tenant rework of that relay so a single relay deployment can serve many independent Mac agents/users with hard routing-layer isolation between them. See [overview](../overview.md) and [bridge](../components/bridge.md) for the current, shipped state of this architecture.

## Body

### Motivation

`cmux` (manaflow-ai/cmux, GPLv3) already ships a mobile-remote system, but the official mobile client is iOS-only and its remote transport is Tailscale-only by policy, not by protocol necessity. Exploration of the source established that cmux's actual security boundary is an account (Stack Auth) token, not the network, and that its transport is abstracted (`CmxByteTransport`); the Tailscale requirement lives in `remotes add` policy, not the wire protocol. This created an opening: build an independent client against cmux's already-documented local control socket / CLI (`cmux rpc`, `cmux events`, mobile RPC methods like `mobile.workspace.list`, `mobile.terminal.*`, `feed.*.reply`) without touching Tailscale, Stack Auth, or cmux's internals, and without becoming a derivative GPL work.

The first-order need was: from anywhere, list cmux sessions, interact with a live terminal, and get notified of + respond to AI-agent prompts — driving the Mac-side bridge. The second-order need came from where the Mac actually lives: behind home NAT, not publicly reachable — an always-on relay the Mac dials *out* to was needed so the phone could reach it from anywhere through a single mTLS nginx endpoint, with no router changes. The third-order need was a scope expansion: run one publicly-registrable relay so other people wouldn't each need their own home-server relay — the target audience is explicitly "open sign-up, strangers," ruling out "trust the operator" and requiring the relay to become its own CA and to treat cross-tenant leakage as a bug class to adversarially test for.

### Design decisions

**Layer 1 — Mac-side bridge (single binary, single user).** cmux's *documented* CLI contract was chosen over its evolving internal mobile protocol, as the smallest fully-controlled surface. The bridge is a single Go static binary (mirrors cmux's own `cmuxd-remote`); the design doc's stated preference for a direct Unix-socket v2-RPC client (lower keystroke latency) was resolved in the implementation plan by adopting the CLI-subprocess fallback outright — the one point where the plan diverges from the design doc's stated preference. Auth is layered: mTLS at nginx (primary edge gate) + a per-device bearer token at the bridge, since "the bridge trusts network position for nothing." Pairing uses a one-time short code exchanged once for a long-lived device token. The cmux write surface is restricted to read-only + terminal I/O + feed replies only — never create/close/restore — a non-negotiable constraint carried into the whole project's invariants. Terminal payload shape was resolved as render-grid cell snapshots (`format: "cmux.render-grid.v1"`) so the app depends only on the bridge, never cmux internals. "Agent needs you" detection uses a frame classifier over `kind ∈ {permissionRequest, question, exitPlan}` plus pending status, or notification-text pattern matching, since cmux has no single explicit "blocking" flag. Push uses Firebase Cloud Messaging HTTP v1, high-priority data messages.

**Layer 2 — Rendezvous relay (v2 topology).** The pivotal insight: a yamux stream satisfies `net.Conn`, and a yamux session satisfies `net.Listener`. This let the existing bridge handler be reused completely unmodified on the wire — the Mac agent serves its existing `server.Handler()` over the tunnel via `http.Serve(session, handler)`, and the relay is just an `httputil.ReverseProxy` whose `Transport.DialContext` opens a fresh yamux stream per proxied request. WebSocket upgrades pass through transparently because gorilla's upgrade only needs `http.Hijacker`, which `http.Serve` provides. The Mac dials out a single persistent WSS to the relay (`/agent/tunnel`); the app connects inbound to the relay over the domain — neither endpoint needs an inbound public port except the relay's nginx. Multiplexing uses `hashicorp/yamux` over the one WSS connection. The same nginx mTLS endpoint and CA serve both the Mac agent and phone devices ("one edge, one CA") — the Mac is treated as a remote client, never assumed to be on the LAN. nginx forwards `X-Client-Cert-CN`, which the relay parses to separate the agent's tunnel route from device API routes. The relay injects `X-Relay-Token` on every proxied request; the agent's handler rejects requests lacking it, as defense in depth. Session cardinality in v1 was exactly one active agent session (a new tunnel replaces and closes the prior one) — an explicit scope limit later revised by the multi-tenant layer. Offline behavior is a clear `503 {"error":"agent_offline"}`, no queueing, no Wake-on-LAN. Push ownership moved from the bridge to the relay: the relay opens its own `/events` subscription over the tunnel independent of any app connection.

**Layer 3 — Multi-tenant transport isolation.** Scoped explicitly to transport/routing isolation only ("Layer 1" in the design doc's own terms) — not end-to-end content encryption or self-service QR pairing, which are scoped as a separate follow-on (see [pairing-e2e-encryption](./pairing-e2e-encryption.md)). The relay becomes its own CA (`internal/ca`, ECDSA P-256 root, 10-year validity): `SignCSR` ignores any CN the CSR itself requests and always assigns the CN the caller (relay) decides, preventing a hostile registrant from requesting another tenant's identity — verified by a dedicated test. Each Mac agent gets a unique per-tenant client cert, CN = `agent:<random-tenant-id>`, replacing the single shared `agentCN` constant from the v2 relay design. Registration uses a new no-mTLS bootstrap surface (`POST /tenants/register`, separate nginx vhost, deliberately reachable without a client cert): an unregistered agent generates its own ECDSA keypair + CSR locally, submits the CSR only, and the relay mints a tenant and signs a cert in response — private keys never cross the wire. Session routing resolves the destination strictly from the authenticated device's `TenantID` (looked up via its bearer token), never from "whichever tunnel is currently up" — a structural guarantee, not a convention. Storage moved from a flat JSON device-token file to embedded SQLite (`modernc.org/sqlite`, pure Go, no cgo), safe under concurrent writes across many tenants. Bearer tokens are hashed at rest (SHA-256); the raw token is returned once, at issuance, and never persisted. Per-cert-serial revocation with stable tenant-ID preservation is an explicit non-goal — re-registering mints a new tenant ID. FCM push was rescoped from a global token list to `Store.TenantFCMTokens(tenantID)` after a leak was found (see Implementation notes). The testing bar includes an explicit adversarial cross-tenant test (`multitenant_test.go`) — per this repo's CLAUDE.md, this test "must always pass — it enforces tenant isolation, not just a test."

**Blind-relay / E2E encryption (separate spec, design-only in these docs).** `docs/superpowers/specs/2026-07-01-multi-tenant-relay-design.md` additionally specifies a Layer-2 content-encryption architecture (X25519 identity keys, QR-pairing, ECDH+HKDF, XChaCha20-Poly1305 AEAD, relay blind to content but still seeing routing metadata) — chosen over a fully opaque byte-pipe as a smaller, lower-risk change. This spec is design-only in these six documents; the actual implementation and its several deviations from this design are covered in [pairing-e2e-encryption](./pairing-e2e-encryption.md). Three further sub-projects (self-service onboarding/abuse resistance, rate limiting/quotas, audit/retention/ops) are named as explicitly out of scope and un-planned as of these docs.

### Implementation notes

Everything lives in one Go module, `github.com/sodre90/term-bridge`, under `bridge/`, shipping two binaries from one tree: `cmd/term-bridge` (Mac agent) and `cmd/term-bridge-relay` (relay). Key packages: `internal/cmux` (the only seam that shells out to the real `cmux` CLI, tested against a fake `cmux` script, never the real binary), `internal/auth` (device/tenant store), `internal/server` (the stable HTTP/WS handler; gained a "trusted mode" `TrustedHandler(relayToken)` swapping device-bearer auth for `X-Relay-Token`), `internal/push` (FCM sender), `internal/tunnel` (WS↔`net.Conn` adapter + yamux dial/accept), `internal/relay` (`Registry`, reverse proxy, CN routing, push monitor), and `internal/ca` (added in the multi-tenant plan).

Stable JSON contract the app depends on: `Session {id, cwd, title, kind, needs_attention}`, `EventFrame {type, needs_attention, feed_id, workspace_id, title, kind, raw}`, `TerminalDown {type, grid, columns, rows}`, `TerminalUp {type, text, columns, rows}`, `FeedReply {kind, request_id, decision, text}`.

Testing discipline across all three plans: strict TDD, zero real network egress, zero real cmux, zero real FCM, in-memory `httptest` servers and `net.Pipe()`-backed yamux sessions. `go build ./... && go vet ./... && go test ./...` gates every commit.

**Bugs found and fixed during implementation** (documented directly in the plans):
- A copy-paste config bug: the relay's `TokenStore` default pointed at the agent's config dir instead of the relay's; fixed while already touching that code.
- A cross-tenant FCM push leak: the attention-fanout called a global `Store.FCMTokens()` with no tenant identity threaded through, so one tenant's event would have paged every tenant's phones. Found by a task reviewer after the relevant task was already implemented and approved; fixed by threading `tenantID` through the whole call chain.
- A cross-tenant HTTP connection-pool leak: `httputil.ReverseProxy`'s transport pooled idle connections keyed only by a constant `"agent"` host string for every tenant, so tenant B's request could ride tenant A's already-open pooled connection without the per-request `DialContext` tenant check running again. Found by the plan's own adversarial isolation test failing exactly this way on first run; fixed with `DisableKeepAlives: true`, forcing a fresh dial/tenant-resolution on every request — documented as a deliberate example of why the adversarial test, not just a design read, was necessary.

Deploy artifacts: a launchd `.plist` for the original single-Mac bridge; a systemd unit + nginx mTLS vhost + example configs for the v2 relay; a second, separate no-mTLS nginx vhost exposing only `/tenants/register` for multi-tenant bootstrap, with a comment flagging rate limiting/abuse resistance there as a known, tracked gap.

CLI surface evolution: `term-bridge {serve|pair|devices|version}` (v1) → `term-bridge {agent|serve|version}` + `term-bridge-relay {serve|pair|devices|version}` (v2) → `term-bridge-relay {serve|pair -tenant <id>|devices|tenants {list|revoke}|version}` (multi-tenant).

### Status

Shipped, per the docs' own markers: the original `term-bridge` plan and the v2 `term-bridge-relay` plan each end with an explicit `## Execution` section stating they were executed inline, task-by-task with TDD and a commit per task, plus a self-review marking every design-doc requirement ✓. The multi-tenant transport plan has no equivalent execution section, but its self-review notes describe concrete, dated, in-session events (a reviewer catching the FCM leak, a test failing on first run) that are strong evidence of real execution. This is corroborated outside these six documents: this repo's `CLAUDE.md` lists `internal/relay/multitenant_test.go` as a non-negotiable invariant, which only makes sense if that file exists in the shipped codebase, and [overview](../overview.md)/[bridge](../components/bridge.md) describe this architecture as the current, live state of the system.

Design-only / not confirmed implemented in these docs: the Layer-2 blind-relay content-encryption design has no accompanying implementation plan among these six documents (see [pairing-e2e-encryption](./pairing-e2e-encryption.md) for what was actually implemented, which deviated from this design in several security-relevant ways). Three further sub-projects (self-service onboarding/abuse resistance, rate limiting/quotas, ops) are explicitly out of scope with no specs found among these files.

**Discrepancies between docs, flagged rather than silently resolved:**
1. The android-bridge design doc states a direct Unix-socket v2-RPC client is *preferred*; the implementation plan goes straight to the CLI-subprocess design with no documented evidence the direct-socket path was attempted first.
2. The v2 relay design doc specifies distinct `AgentConfig`/`RelayConfig` types; the implementation plan instead extends the pre-existing single `Config` struct — functionally equivalent, but a structural deviation.
3. The single-tenant `agentCN` model from the v2 relay design is superseded by the multi-tenant plan's per-tenant `agent:<tenant-id>` CNs — a documented, intentional evolution, not a contradiction.
