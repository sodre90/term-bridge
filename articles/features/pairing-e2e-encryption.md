## Summary

Self-service QR-code device pairing and end-to-end (e2e) content encryption between the Android phone app and `term-bridge agent`, through the untrusted `term-bridge-relay` home-server daemon. It replaced an operator-driven manual pairing flow (hand-rolled CSR/`.p12` client certificates, a `term-bridge-relay pair` CLI, out-of-band token transfer) with scan-a-QR-code pairing, and added a cryptographic layer (X25519 ECDH + HKDF-SHA256 + XChaCha20-Poly1305 AEAD) so a compromised or malicious relay operator can read only transport metadata, never session/terminal/event content. A later security review found and fixed a Critical gap in the pairing handshake itself (relay-mediated MITM of the key exchange), closed via mutual SAS/fingerprint confirmation. See [overview](../overview.md) for how this fits into the shipped security model, and [bridge-relay-architecture](./bridge-relay-architecture.md) for the relay this pairs through.

## Body

### Motivation

The multi-tenant relay migration (see [bridge-relay-architecture](./bridge-relay-architecture.md)) implemented per-tenant transport isolation but deliberately deferred end-to-end content encryption and self-service phone pairing UX. Before this work, pairing required an operator to hand-craft a CSR/`.p12` via `openssl`, run `term-bridge-relay pair` to mint a bearer token, and manually transfer both out-of-band — and only transport (mTLS) was protected, not content. This project closed both gaps together: QR-based self-service pairing (the agent renders a QR in its terminal; the phone scans it) and e2e content encryption so the relay — even fully compromised — is blind to everything except HTTP routing metadata and the WebSocket upgrade.

Two follow-on problems then drove further work. First, a dedicated 31-agent, 7-dimension multi-agent security review found that the pairing key exchange itself — plain unauthenticated ECDH — could be MITM'd by a fully malicious relay on both legs of trust, not just the manual-entry path informally suspected; this is the Critical finding the SAS-fingerprint work fixes. Second, Google deprecated `androidx.security.crypto` (the library storing this app's tokens and key material at rest), prompting a still-unimplemented migration design.

### Design decisions

**Cryptographic primitives.** Key exchange is X25519 ECDH — each side generates and persists a long-term identity keypair. Key derivation is HKDF-SHA256 over the raw ECDH output, salt=nil, with an `info` string that binds both public keys, sorted lexicographically, so both peers derive an identical `info` regardless of which side computes it. AEAD is XChaCha20-Poly1305 (24-byte nonce), applied to every HTTP body and every terminal/events WebSocket frame.

**Direction-tagged nonces (a security-critical deviation from the original spec).** The approved parent-spec text described a nonce of 16 zero bytes + an 8-byte counter, one shared key for both directions, each direction's counter starting independently at 0. The implementation plan flags this explicitly as insecure and not followed: it would cause the agent's first message and the phone's first message to both be sealed under nonce=0 with the same key — catastrophic AEAD nonce reuse. What was actually implemented puts a direction tag at byte 15 of the nonce (`DirAgentToDevice = 0x00`, bit-identical to the original all-zero prefix; `DirDeviceToAgent = 0x01`, a fully disjoint nonce space under the same key). Both implementations note this is perspective-relative and easy to get backwards.

**Durable, shared-not-per-connection counters (a second deviation).** The literal spec said the WS frame counter resets to 0 on reconnect, under an assumption that shared secrets lived only in memory. Because the implementation persists the shared secret to disk, resetting counters to 0 on reconnect would reuse `(direction, counter)` nonce pairs across connections — the same class of bug as the direction-tag issue. The fix: one monotonic send counter per direction per device, persisted, shared by both the HTTP body envelope and every WS connection's frame envelope; counters never reset.

**Sliding-window replay protection (a third deviation, phone-driven).** The original design used strict monotonic counter validation. This breaks once a phone has three concurrent agent→device channels (HTTP responses, `/terminal` WS, `/events` WS) drawing from one agent-side send counter with no cross-channel ordering guarantee. The fix, applied identically on Go and Android, replaces strict monotonicity with an RFC 6479-style sliding acceptance window (W = 64): track `highestSeen` plus a 64-bit `windowBits` mask. Validation (`canAccept`) is strictly read-only; commit is a separate, mutating call that must only run after the AEAD tag has verified successfully — this two-phase split is a hard invariant on both sides, so a corrupted or forged message can never permanently desync the legitimate sequence. **Note:** this in-repo synthesis of the original design docs describes the validate/commit split as already atomic-safe by construction; the [app-polish-and-hardening](./app-polish-and-hardening.md) and [enhancement-audit](../enhancement-audit.md) material identifies a real concurrent TOCTOU race between separate validate and commit lock cycles in the shipped Go implementation — the two-phase invariant held at the design level but the initial implementation's locking did not yet enforce it atomically.

**Pairing handshake / data flow.** The agent requests a pairing code from the relay and renders a QR in its terminal containing `{code, agent_pubkey, expires_at, tenant_id, pair_url}`. The phone scans it (CameraX + ML Kit, on-device, QR-only), generates its own X25519 keypair, and POSTs `{code, name, device_pubkey}` to the relay (deliberately unauthenticated — the phone has no token yet, mirroring the `/tenants/register` bootstrap pattern). The relay redeems the code (non-destructive, UPDATE-based, so the row survives for polling), mints a bearer token, and returns `{token, tenant_id}`. The agent's `pair-device` CLI polls until it sees the device's public key, then independently derives the shared secret via ECDH. Both sides compute `ECDH(agentPriv, devicePub) == ECDH(devicePriv, agentPub)` independently — the raw shared secret never crosses the relay; the relay only ever sees public keys and ciphertext.

**Android crypto library split (BouncyCastle + lazysodium, not Tink).** Tink was rejected: its `Aead` interface manages its own nonces internally with its own framing, and there is no supported way to hand it a caller-constructed direction+counter nonce. BouncyCastle was empirically verified against the Go side's fixed test vectors to correctly reproduce X25519 ECDH and HKDF-SHA256 byte-for-byte, but has no XChaCha20-Poly1305 implementation in any version. `lazysodium-android` (a JNA binding to real libsodium) was verified byte-identical to Go's `chacha20poly1305.NewX` for the AEAD piece. Hand-rolling XChaCha's HChaCha20 subkey derivation atop BouncyCastle's raw ChaCha engine was explicitly rejected as the same kind of custom-crypto risk that ruled out Tink.

**MITM threat model and the SAS/fingerprint fix.** A 31-agent, 7-dimension security review found that standard ECDH provides confidentiality against passive eavesdroppers but no authentication — a relay that independently substitutes keys on both legs (computing both resulting secrets itself) mounts a textbook MITM. Two independent, both-exploitable trust legs were found: (1) the phone's belief about the agent's key — the QR-scan path is safe (the relay never mediates it), but the manual pairing-code entry path (`GET /devices/pair-info/{code}`, added later with no accompanying design doc) trusts whatever `agent_pubkey` the relay's own state reports; (2) the agent's belief about the device's key — exploitable unconditionally, on every pairing regardless of QR or manual entry, since the CLI's only source of truth is the relay-owned `device_pubkey` field, with no cryptographic tie-back to a real phone; a fully malicious relay could fabricate an entire phantom pairing.

Four directions were evaluated: mutual SAS/fingerprint confirmation (recommended and implemented); removing manual entry alone (rejected — only closes leg 1); cryptographically binding the pairing code with a MAC/signature (rejected — pairing is a first-contact bootstrap with no pre-shared secret, and any relay-transported data is attacker-controllable under the fully-malicious-relay threat model); TOFU + out-of-band new-device notification (deferred as future defense-in-depth). The fingerprint function is order-independent (lexicographic min/max of the two raw pubkeys, SHA-256, formatted as 3 groups of 2 hex bytes — 48 bits), displayed on both the CLI (interactive `[y/N]` prompt) and a new Android `AwaitingConfirmation` screen state; neither side commits trust until a human confirms the two displayed strings match. 48 bits (versus Signal's ~199-bit safety numbers) defends against an active, real-time forgery attempt bounded by the pairing deadline (default 5 minutes) — a different, much narrower threat model than Signal's long-lived identity keys against nation-state precomputation. Deliberately no `--yes`/non-interactive bypass flag was added, since a repo-wide grep found zero scripted `pair-device` invocations. The CLI's rejection path has an accepted asymmetry versus Android's: because `RedeemPairingCode` has already run by the time the CLI's poll reports `redeemed: true`, a rejected fingerprint on the CLI cannot un-consume the pairing code (only stops persisting the shared secret); Android's rejection makes zero network calls at all. This asymmetry is named as a real gap overlapping a separately-tracked High finding (no practical single-device token revocation).

**At-rest storage migration (design-only).** A separate spec addresses `androidx.security.crypto`'s deprecation. It evaluates Tink directly (rejected — machinery sized for scenarios this app doesn't have) versus DataStore + a hand-managed AES-256-GCM Android Keystore key (recommended — matches Google's own replacement guidance, replaces the aging SharedPreferences layer too, small/readable new crypto code mirroring the existing `data/e2e/Cipher.kt` pattern). The design specifies a required in-place migration for existing paired installs (detect old file → read via old API → write new record transactionally → verify in-memory → delete old file only after verification, modeled on the existing self-terminating migration pattern already in the codebase). This document states explicitly that it accompanies no production code changes and is a "Plan (don't yet execute)" deliverable only.

### Implementation notes

**Key storage.** Go agent: a persistent X25519 identity keypair as a raw 32-byte file, 0600 permissions, at `~/.config/term-bridge/identity.key`. Paired-device shared secrets, per-device send counters, and sliding-window receive state live in `bridge/internal/e2e/store.go`, a JSON file with no in-memory caching — every method re-reads the full file and writes back atomically (temp file + rename) on every call, so the long-running agent process and the separate `pair-device` CLI invocation see each other's writes with no reload mechanism. A narrow last-write-wins race under concurrent writers is explicitly accepted per this project's risk tolerance — no file locking was added at the design stage (see [app-polish-and-hardening](./app-polish-and-hardening.md) for the later SQLite-migration proposal addressing exactly this). Android: `Identity.kt` persists the phone's identity keypair via `EncryptedSharedPreferences`; `Session.kt`/`CryptoSession.kt` holds the shared secret, durable send counter, and sliding-window state, also `EncryptedSharedPreferences`-backed, with an in-memory mirror of the counter/window fields for the hot path so encryption never blocks on Keystore I/O. `peer_pubkey`/`shared_secret` are deliberately not cached in memory, read synchronously from prefs for read-after-write consistency.

**Wire formats.** HTTP body envelope: JSON `{"v":1,"n":<uint64>,"ct":"<base64 ciphertext+tag>"}`. WS binary frame: `[8-byte big-endian counter][ciphertext+tag]`. A decryption failure returns `400 {"error":"decrypt_failed"}` on Go and short-circuits before reaching the cmux handler; on Android, `E2eInterceptor` throws `IOException` for HTTP while `TerminalSocket`/`EventsSocket` drop and log a single corrupted/out-of-window frame rather than tearing down the connection.

**File/package layout.** Go (`bridge/internal/e2e/`): `identity.go`, `cipher.go` (nonce/ECDH/HKDF/AEAD/`PairingFingerprint`), `store.go`, `envelope.go`, `frame.go`, each with a matching test file. Relay routes in `internal/relay/relay.go`; `internal/auth/store.go` gained a `device_pubkey` column and a non-destructive `RedeemPairingCode`. `cmd/term-bridge/pair.go` holds the interactive CLI, including the fingerprint-confirmation gate that fails closed on EOF/any non-`y`/`yes` input. The old `term-bridge-relay pair` CLI was deleted outright, an accepted lockout of any phone still on the old flow. Android (`android/app/src/main/java/com/sodre90/cmuxremote/`): `data/e2e/` (`Cipher.kt`, `Identity.kt`, `ReplayWindow.kt`, `Session.kt`/`CryptoSession.kt`, `Envelope.kt`, `Frame.kt`, `E2eInterceptor.kt`), `data/pairing/` (`PairingQr.kt`, `PairingClient.kt`, later split into a network-free `prepare()` computing the fingerprint and a `commit()` doing the POST/derive/persist), `ui/pairing/` (`PairingViewModel.kt`, `PairingScreen.kt`), replacing the old Settings-screen onboarding. `Mtls.kt`'s `.p12` client-cert loading was deleted; the app is bearer-token-only, matching the relay's nginx change to `ssl_verify_client optional`. Confirmed present in the current codebase by direct inspection at the time these docs were written.

**Nginx/relay hardening accompanying rollout.** `ssl_verify_client` was relaxed from `on` to `optional` on the main vhost so a certless phone can reach the relay. This is not a free simplification: with `optional`, nginx forwards `X-Client-Cert-CN` for any presented certificate, verified or not, so a trivial self-signed cert could otherwise spoof an agent tenant. The fix adds `X-Client-Cert-Verify` forwarding and a `verifiedAgentTenant` helper every agent-CN-trusting path must go through, requiring `X-Client-Cert-Verify == "SUCCESS"`.

**Testing approach.** Cross-language interop is proven via fixed test vectors: the Go `internal/e2e` tests hardcode private keys, expected public keys, an expected shared secret, and expected AEAD ciphertext; Kotlin's `CipherTest.kt` reproduces the identical values byte-for-byte — the explicit mechanism proving both independently-written implementations interoperate, since no automated cross-language test exists. Sliding-window replay logic is unit-tested in isolation from storage on both sides. No end-to-end/instrumented tests exist for either the pairing flow or the crypto layer on either side — verification against real hardware is manual, post-merge. The SAS-fingerprint plan adds order-independence/distinct-input property tests, a hand-verified golden fixed-input/output case on both languages, an Android test asserting rejection makes zero network calls, and Go tests asserting `AddDevice` is only called on confirmation and that EOF/garbage stdin fails closed.

### Status

**Shipped**, per the docs' own markers and direct codebase inspection at the time of writing: Go-side pairing + e2e (fully merged into the multi-tenant relay transport branch, `bridge/internal/e2e` package and tests present); Android-side pairing + e2e (full `data/e2e`/`data/pairing`/`ui/pairing` package structure present); the SAS/fingerprint MITM fix (`PairingFingerprint` present on both sides, `AwaitingConfirmation` state present, matching commit `e2e: require SAS fingerprint confirmation before trusting a pairing key`).

**Note on two similarly-named plan documents:** `2026-07-02-android-device-pairing-e2e-encryption.md` and `2026-07-02-device-pairing-e2e-encryption.md` are not duplicates and neither supersedes the other — they are sequential, complementary plans split by side (Go/relay/agent first, 16 tasks; Android/Kotlin client second, 19 tasks, the last of which amends the already-shipped Go store to switch its replay gate to the sliding window the Android side needed). The Go plan had to land first since the Android plan builds against its already-shipped endpoints/wire format.

**Design/proposal only, not implemented:** the `security-crypto` migration — confirmed against the codebase at the time of writing: no `androidx.datastore` dependency exists, and the three `EncryptedSharedPreferences`-backed classes are unchanged.

**Related item surfaced but not detailed in these docs:** manual pairing-code entry (`GET /devices/pair-info/{code}`) was added after the original pairing cycle in a separate, undocumented commit — the feature whose addition reopened part of the MITM gap the SAS-fingerprint work later closed.

**Explicitly still open** per the SAS-fingerprint plan's non-goals: single-device bearer-token revocation (a separately-tracked High finding from the same review), TOFU-style new-device push notifications, and un-burning a pairing code on CLI rejection. Six further lower-severity findings from the same review (rate limiting, `FLAG_SECURE`, WS message-size limits, unsanitized route IDs, exported `MainActivity` intent extras, relay server timeouts) are explicitly out of scope for the fingerprint fix.
