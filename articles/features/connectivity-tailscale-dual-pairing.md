## Summary

Two linked connectivity projects for the transport layer: Tailscale-direct transport adds an optional second listener to `term-bridge agent` so the phone can talk straight to the Mac over a Tailscale tailnet, bypassing the relay and home server entirely; dual-pairing automatic fallback builds on top of it so the Android app pairs against both relay and direct simultaneously and automatically fails over between them with no user action. See [overview](../overview.md) for how Direct (Tailscale) mode fits the shipped feature set, and [bridge-relay-architecture](./bridge-relay-architecture.md) for the relay this is an alternative to.

## Body

### Motivation

The app's only transport was the agent dialing out to the relay over a yamux-over-WSS tunnel — chosen originally to avoid requiring Tailscale, a home server, or router changes, deliberately diverging from cmux's official iOS app's Tailscale-only policy. The user was now running (or willing to run) Tailscale on both the Mac and phone and wanted a second, optional transport for the common case where both devices are reachable on the same tailnet right now, avoiding the relay/home-server dependency for that case while leaving the relay fully intact for reachability elsewhere and for push.

Once direct mode existed and was live-tested, a design gap became a real bug: the phone could only store one `{baseUrl, deviceToken}` pairing at a time, so pairing against direct mode silently discarded the relay pairing and vice versa — switching required a manual re-pair. This also surfaced a correctness bug: direct mode has no `/devices/register` (FCM) endpoint, since push is relay-only by design, yet the app's two push-registration call sites blindly used "whatever bridge is currently configured" — a phone paired only to direct would silently and permanently lose push on the next FCM token refresh, because the failure was caught and swallowed. The user's own request captured the target: "if my home server down, I can access it through tailscale as fallback" — automatic relay-primary/direct-fallback behavior, not a manual switch to remember.

### Design decisions

**Tailscale-direct transport.** Additive, not a replacement: `direct_listen` unset (the default) produces byte-for-byte identical agent behavior; the relay dial loop and all existing relay/push code paths are untouched. No `tsnet`, no embedded WireGuard — the bridge uses only `tailscale.LocalClient`, talking to the Mac's already-running system `tailscaled` over its local API socket; the phone uses the official Tailscale Android app, no new Android networking library, no app code changes for the network layer itself. TLS uses real Tailscale certs, not self-signed: with MagicDNS + "HTTPS Certificates" enabled in the tailnet admin console, `tailscale.LocalClient.GetCertificate` implements `tls.Config.GetCertificate` directly, giving the Go listener a real, publicly-trusted Let's Encrypt cert for `<node>.<tailnet>.ts.net`, auto-provisioned/renewed — this is precisely what makes the Android side a no-op: ordinary HTTPS validated by system root CAs, no custom trust anchor. Auth without a relay Director in front required one genuinely new piece of plumbing: an `injectDeviceID` middleware that reads the already-verified device out of request context and overwrites any client-supplied `X-Device-ID` before the encryption middleware runs, so a device can prove its own bearer token but cannot spoof another device's ID. Everything else (`auth.Store`, `e2e.Store`, `encryptionMiddleware`, routes) is reused verbatim. Direct mode's local `auth.Store` (a separate SQLite DB) has exactly one implicit tenant — this Mac — auto-created on first use; the pairing handlers are near-verbatim ports of the relay's equivalents minus the mTLS-CN tenant-resolution gate, since there's no second tenant to disambiguate and the real access boundary is Tailscale's own network ACLs. The security implication of bypassing the relay is explicitly named and accepted: the relay's mTLS/proxy trust boundary is replaced by Tailscale's own network-layer WireGuard encryption and ACLs, a real publicly-trusted TLS cert, and the same bearer-token + e2e-AEAD layers used everywhere else; a device paired via the relay cannot use its token against the direct listener or vice versa, since the two `auth.Store`s are entirely separate databases. Push stays relay-only — the agent holds no FCM credentials in direct mode (later revisited, see [push-notifications](./push-notifications.md)). Switching between transports in v1 was a manual re-pair, explicitly named as deferred.

**Dual-pairing automatic fallback.** Fixed roles, not configurable priority: relay is always primary, direct is always fallback, matching reality (relay works from any network; direct only works when Tailscale is up on the phone). Both slots are independently paired credentials — there's no way to derive one from the other, a direct consequence of direct-transport's tenant isolation. HTTP fallback is via a wrapper, not per-call-site logic: `FallbackBridgeClient` wraps primary/fallback suppliers, tries primary first, and on `IOException` retries the identical call against fallback, recording an in-memory "primary is down" timestamp for a 30-second penalty window so a dead relay isn't re-tried on every call within that window — process-lifetime only, no persisted "which worked last" state (a deliberate non-goal). The relay-slot OkHttp client gets a short (3s) explicit connect timeout so a dead relay fails fast; the direct slot keeps OkHttp's normal default since there's no second fallback to race once already on direct. WebSocket fallback is via loop alternation, not the wrapper: `EventsSocket`/`TerminalSocket`'s existing reconnect-with-backoff loops each track a preferred slot (starting `RELAY`) and flip it on any connection failure — kept as three small, near-identical diffs across the three ViewModels rather than a shared abstraction, matching this codebase's existing style. Push registration is pinned to the relay slot unconditionally at both call sites; if the relay slot isn't paired, this is now silently *correct* (push unavailable, matching reality) instead of silently *wrong*. No bridge (Go) changes were required for this half — both listeners already run concurrently and independently; this is a client-side connection-selection problem. The design doc explicitly flags its core premise as **not confirmed**: "Automatic fallback, not a manual switcher… (Proposed and not yet explicitly confirmed in chat — the prior AskUserQuestion on this timed out; please confirm or redirect when reviewing this spec.)"

### Implementation notes

**Config/data model (bridge, Go).** `AgentConfig` gains `DirectListen string` (`direct_listen`, e.g. `":8443"`, empty = disabled) and `DirectAuthStore string` (default `~/.config/term-bridge/direct-auth.db`). `runAgent` opens `directStore` and calls `ensureDirectTenant` only when `DirectListen` is set; `server.New`'s third argument becomes that store (was nil). A `serveDirect` goroutine wraps a TLS listener using `lc.GetCertificate`, mounts direct pairing plus `srv.DirectHandler()`, and runs alongside the unchanged relay dial loop. Wire shapes for the four new pairing endpoints were required to exactly match the relay's existing types, since both `pair.go`'s `pairDevice()` and Android's `PairingClient.kt` must work against either backend unmodified. CLI: `pair-device` gains a `--direct` flag, resolving the agent's base URL via Tailscale status instead of the relay URL, using a plain HTTP client (no client-cert/mTLS setup) since the cert is publicly trusted.

**Pairing/config data model (Android, Kotlin).** A new `ConnectionSlot` enum (`RELAY`, `DIRECT`) with `other()` and a heuristic `inferLegacySlot(baseUrl)` (a `.ts.net` host infers `DIRECT`, everything else infers `RELAY`). `Settings` and `Session` move from single unprefixed keys to slot-prefixed keys, each exposing a one-time, self-terminating migration reading old bare keys once and deleting them — run explicitly by `AppContainer` at construction. `AppContainer` builds one `OkHttpClient` per slot, exposes `bridgeClient(slot)`, `eventsSocket(slot)`, `terminalSocket(slot, id)`, `pairingClient(slot)`, plus `activeBridge(): FallbackBridgeClient?` (null only when neither slot is paired) and `anyBridgeConfigured()`. `PairingClient` gains a `slot` constructor parameter. A new `ConnectionSettingsScreen` replaces the old single-pairing Settings screen, showing both slots' paired/unpaired status with independent (re)pair buttons; nav-host start destination becomes Settings only if neither slot is paired.

**Testing approach.** Bridge: task-by-task TDD — config parsing, `DirectHandler` (missing bearer → 401, forged `X-Device-ID` overwritten not honored, unpaired device → 409), and the four pairing handlers mirroring the relay's own handler tests. No automated test for the Tailscale cert path itself or `pair-device --direct`'s flag parsing beyond a build/help smoke check — real end-to-end pairing was deferred to manual verification with real devices. Android: `ConnectionSlotTest` (5 cases including an adversarial `"ts.net.evil.example.com"` substring-vs-suffix case) and `FallbackBridgeClientTest` (8 MockWebServer cases with an injectable clock, covering primary-success, primary-failure-then-fallback, both-fail, single-slot-configured, penalty-window skip/expiry). `Settings`/`Session`/`AppContainer`/push-registration changes have no automated coverage — no Robolectric configured; verified by inspection plus full-suite green. Manual end-to-end (both projects): pair against direct, stop the relay while keeping Tailscale up, confirm sessions/terminal/feed replies keep working; confirm push still arrives via the relay while paired in direct mode.

### Status

Based strictly on the documents' own internal markers: **Tailscale-direct transport** is presented as an unchecked-checkbox plan, but the dual-pairing design doc's own Context section states, as an established fact predating that second project: "Real end-to-end testing (2026-07-04) confirmed direct mode itself works — including a real Let's Encrypt cert served over the tailnet." This is the only self-referential completion evidence found for direct-transport in these four documents. **Dual-pairing automatic fallback** is also an unchecked-checkbox plan, and its design doc explicitly flags the core premise as not confirmed (see Design decisions above) — no later self-referential statement in these four documents confirms this shipped or was end-to-end tested. Both plans' final verification sections describe manual, real-device testing as the intended acceptance check, but neither document records the outcome. See [overview](../overview.md) for the current README's framing of Direct (Tailscale) mode as a shipped, documented feature, which is later external evidence beyond these four documents.
